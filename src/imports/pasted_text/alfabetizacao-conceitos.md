O Problema de Identificação (Tópico 1) é o coração do sistema, pois consiste em transformar a sensibilidade do olhar docente em um diagnóstico automatizado preciso. O desafio central é que a criança não escreve de forma linear; ela testa hipóteses. Por isso, identificar o nível de cada uma exige que o software diferencie o Pré-Silábico do Silábico não pela correção da escrita, mas pela lógica da contagem. No estágio pré-silábico, o sistema deve notar que a criança usa letras de forma aleatória e puramente visual, sem entender que a escrita representa os sons da fala. Já a transição para o nível silábico ocorre quando o sistema detecta que a criança estabelece uma regra quantitativa: para cada vez que ela abre a boca (uma sílaba), ela coloca exatamente uma letra, independentemente de qual seja. A complexidade aumenta ao tentar diferenciar o Silábico sem valor do Silábico com valor. No primeiro, o sistema identifica que a criança mantém a contagem de uma letra por sílaba, mas as letras não possuem relação com o som da palavra real (ex: usar "PX" para "BOLA"). No segundo, o software precisa cruzar a resposta com um banco de dados fonético para validar que as letras escolhidas já representam o som da sílaba, como as vogais (ex: usar "OA" para "BOLA"). O software deve compreender que uma única resposta nunca é suficiente para essa identificação, pois a criança pode acertar por sorte ou errar por distração; portanto, o sistema deve exigir um padrão de comportamento em múltiplas tentativas com palavras de diferentes tamanhos para confirmar o estágio real de aprendizagem. 

O Problema de Interpretação do Erro (Tópico 2) na didática do sistema muda a visão tradicional de "certo ou errado" para uma visão de diagnóstico construtivo, onde o erro é a ferramenta principal para entender a lógica da criança. No contexto de um jogo, isso significa que o sistema não deve apenas sinalizar uma falha, mas sim analisar a natureza daquela escrita para identificar a hipótese que a criança está testando. Por exemplo, ao escrever "BRT" para uma palavra como "BONECA", o sistema interpreta que o erro revela um nível pré-silábico, indicando que o aluno já reconhece as letras, mas ainda não as vincula aos sons da fala. Já uma escrita como "CA" ou "CSA" para "CASA" revela estágios mais avançados; no primeiro caso, pode indicar uma falta de percepção da segunda sílaba ou uma escrita silábica inicial, enquanto no segundo, o erro mostra que a criança já está no nível silábico com valor sonoro, pois identificou os sons principais das consoantes, mesmo omitindo as vogais. Dessa forma, a interpretação do erro dentro da didática do jogo serve como um motor de inteligência para mapear em que estágio da psicogênese a criança está transformando o que seria uma falha em uma informação para que o sistema saiba qual intervenção ou atividade sugerir para provocar o avanço para o próximo nível. 

O Problema de Tradução Pedagógica (Tópico 3) exige que as teorias da psicogênese sejam convertidas em regras de código para adotar uma lógica de análise de equivalência. No nível pré-silábico ele detecta o uso de letras, mas valida a ausência de correspondência sonora ou a crença de que palavras maiores exigem mais caracteres. A lógica evolui nos níveis silábicos, onde o sistema programa a regra de uma letra por sílaba, diferenciando a ausência de valor sonoro (letras aleatórias) da presença de valor (letras que compõem a sílaba real). No estágio silábico-alfabético, o código deve ser capaz de processar a instabilidade, aceitando respostas que misturam sílabas completas com representações de apenas uma letra. Por fim, no nível alfabético, a regra lógica passa a ser a representação total dos fonemas, permitindo que o sistema valide a escrita funcional mesmo quando houver divergências ortográficas, fechando o ciclo da tradução teórica para o processamento automatizado. Para evitar interpretações erradas causadas por cliques acidentais ou distração, o sistema aplica um critério de consistência, exigindo que o mesmo padrão se repita em uma sequência de palavras de diferentes tamanhos (polissílabas a monossílabas) antes de confirmar a classificação do nível no histórico do aluno. 

No Problema de Coleta de Dados (Tópico 4), a solução mais adequada para a alfabetização é o uso de um alfabeto móvel digital (arrastar letras), pois o texto digitado via teclado impõe uma barreira motora desnecessária para quem ainda está aprendendo a forma das letras. Deve centrar-se na premissa de que a forma como a criança interage com o dispositivo determina a pureza do dado pedagógico coletado. Em um contexto de alfabetização, a coleta não pode ser passiva ou meramente mecânica; ela deve espelhar o processo de construção do pensamento infantil. Se utilizarmos o texto digitado via teclado, inserimos uma barreira técnica que confunde o diagnóstico, pois a criança pode errar por não encontrar uma tecla, e não por falta de conhecimento fonético. 

O Problema de Usabilidade (Tópico 5) em um sistema de alfabetização reside no desafio de criar uma interface para um usuário que, por definição, ainda não sabe ler. Isso exige que o software abandone a dependência de textos e menus escritos, substituindo-os por uma arquitetura de informação baseada em áudio e imagem. A usabilidade crítica aqui significa que o sistema deve fornecer comandos de voz claros e intuitivos para cada ação, como "clique na figura" ou "arraste as letras para o quadro", garantindo que a criança consiga navegar com autonomia sem o auxílio constante de um adulto. Além disso, o design deve evitar o excesso de estímulos visuais que causem distração, focando a atenção do aluno apenas nos elementos necessários para o exercício de escrita. 

O Problema de Autenticação (Tópico 6) deve ser resolvido eliminando barreiras textuais, como e-mails e senhas, que impedem a autonomia da criança. A solução ideal é o uso de um "mural de fotos" ou avatares personalizados, onde o aluno entra no sistema clicando em sua própria imagem ou em um símbolo previamente escolhido na lista da turma. Esse método garante que a criança acesse seu perfil de forma independente, permitindo que o sistema inicie a coleta de dados sem depender de um mediador para realizar o login. 

O Problema do Feedback (Tópico 7) exige uma abordagem dual: para a criança, o retorno deve ser imediato, lúdico e encorajador, focado na progressão e não no erro, utilizando animações ou sons de conquista. Já para o professor, o feedback deve ser um relatório analítico e técnico, traduzindo o desempenho do aluno em dados sobre seu estágio de alfabetização. Essa separação garante que o aluno mantenha o engajamento emocional enquanto o docente recebe a inteligência necessária para ajustar sua prática pedagógica. 

O Problema de Evolução (Tópico 8) refere-se à capacidade do sistema de detectar os "saltos" de nível da criança. O software deve monitorar os momentos de conflito cognitivo — como quando a criança hesita ou testa mais letras do que o habitual para uma palavra — sinalizando que ela está abandonando uma hipótese antiga para construir uma mais complexa. O monitoramento contínuo permite que o sistema identifique não apenas o nível atual, mas a velocidade e a natureza do progresso individual de cada aluno. 

O Problema de Intervenção (Tópico 9) foca na ação do sistema após o diagnóstico, sugerindo atividades de "desequilíbrio" que desafiem o nível atual da criança. Se o sistema identifica um nível silábico, ele deve oferecer jogos de rimas ou comparação de palavras com estruturas parecidas para forçar a percepção dos fonemas. A intervenção automatizada serve para manter o aluno na zona de desenvolvimento proximal, oferecendo o desafio certo para que ele avance para o próximo estágio da psicogênese. 

O Problema de Personalização (Tópico 10) trata do ajuste do ritmo de aprendizagem às necessidades específicas de cada aluno. O algoritmo deve adaptar a dificuldade dos desafios e a frequência dos feedbacks com base no histórico de erros e acertos, garantindo que a criança não se frustre com tarefas difíceis demais nem se desmotive com repetições desnecessárias. A personalização transforma o sistema em uma trilha de aprendizagem única, respeitando o tempo de maturação biológica e cognitiva de cada estudante. 

O Problema do Histórico de Dados (Tópico 11) exige que o sistema registre não apenas a resposta final, mas todo o rastro do processo de escrita. Salvar as letras que foram arrastadas e depois descartadas, o tempo de hesitação e as substituições feitas permite reconstruir o raciocínio da criança. Esse histórico acumulado é o que possibilita ao professor enxergar a evolução longitudinal, percebendo como a lógica de escrita do aluno se transformou ao longo dos meses. 

O Problema de Informação e Dashboards (Tópico 12) consiste em transformar o volume massivo de dados em visualizações simples e acionáveis para o professor. Os painéis de controle devem mostrar gráficos de progresso da turma, destacar alunos que estão estagnados há muito tempo em um nível e sugerir agrupamentos produtivos (crianças em níveis próximos que podem aprender juntas). O objetivo é que o docente consiga realizar uma leitura rápida do cenário pedagógico para tomar decisões baseadas em evidências. 

O Problema de Validação do Sistema (Tópico 13) envolve a necessidade de comprovar que o diagnóstico automatizado é fiel à realidade. Isso deve ser feito através de testes comparativos (testes A/B) entre a avaliação do software e a avaliação manual de especialistas em alfabetização. A validação contínua garante a confiabilidade pedagógica da ferramenta, permitindo que o algoritmo seja ajustado conforme novas variações de escrita e regionalismos sejam detectados. 

O Problema de Escala (Tópico 14) aborda a robustez necessária para o sistema funcionar em diferentes cenários, desde um único tablet até redes escolares inteiras. A arquitetura de dados deve suportar o armazenamento e o processamento simultâneo de milhares de avaliações sem perda de desempenho, garantindo que o diagnóstico seja entregue em tempo real para o professor, independentemente do volume de alunos conectados. 

O Problema de Explicação do Diagnóstico (Tópico 15) exige que o sistema seja transparente em sua lógica, justificando por que classificou uma criança em determinado nível. Ao entregar o resultado, o software deve apresentar os critérios utilizados, como "o aluno demonstrou escrita silábica com valor sonoro ao representar cada sílaba por uma vogal correspondente". Essa transparência educa o professor e gera confiança na automação pedagógica. 

O Problema de Limite do Sistema (Tópico 16) estabelece a fronteira entre a tecnologia e a atuação humana. O software deve ser programado para identificar casos complexos que fogem ao padrão da psicogênese tradicional — como possíveis dificuldades de aprendizagem ou questões motoras graves — e sinalizar que aquele aluno requer uma avaliação presencial e detalhada do educador, reforçando que a ferramenta é um suporte e não um substituto do diagnóstico clínico. 

O Problema de Foco (Tópico 17) determina que o produto digital deve ter um objetivo claro: diagnosticar e acompanhar a evolução da alfabetização inicial. Evitar que o sistema se torne uma plataforma genérica de conteúdos garante que a ferramenta seja excelente naquilo que se propõe, resolvendo a dor específica do professor em identificar os níveis de escrita com precisão e rapidez. 

O Problema de Experiência (UX) (Tópico 18) foca no engajamento da criança através de uma interface gamificada que torne a avaliação prazerosa. A estética deve ser amigável e a narrativa envolvente, transformando o teste de nível em uma missão ou jornada. Uma boa experiência de usuário reduz a ansiedade do aluno perante o desafio, resultando em produções de escrita mais autênticas e menos inibidas. 

O Problema de Entrada de Dados Pedagógicos (Tópico 19) diz respeito à curadoria dos conteúdos que alimentam o sistema, como as palavras escolhidas para os ditados. Essa seleção não é aleatória; deve seguir critérios linguísticos rigorosos (palavras estáveis, sem dígrafos complexos no início, de diferentes tamanhos) para garantir que o erro da criança seja revelador de seu nível e não apenas uma confusão causada por uma palavra inadequada. 

O Problema de Adaptação ao Contexto (Tópico 20) exige versatilidade tecnológica para que o sistema funcione em ambientes com baixa conectividade ou diferentes dispositivos. A ferramenta deve prever modos de uso offline com sincronização posterior, permitindo que escolas em contextos vulneráveis tenham o mesmo acesso à qualidade de diagnóstico que instituições com infraestrutura tecnológica avançada. 

O Problema de Erro do Sistema (Tópico 21) prevê mecanismos de correção para quando o algoritmo falha na interpretação, como em casos de cliques acidentais. O sistema deve oferecer uma funcionalidade de "ajuste manual do professor", permitindo que o docente altere o nível do aluno caso sua observação em sala discorde do software. Essa soberania do professor garante a precisão final do histórico e permite que a máquina aprenda com as correções humanas.
